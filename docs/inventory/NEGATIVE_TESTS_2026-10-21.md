# Дополнение к протоколу: негативные испытания 21.10.2026

**Источник:** выводы команд CMD, предоставленные Сашей в ходе шагов 36–55. **Среда:** `MTA_inventory_TRIGGER_TEST.db` — копия успешно завершённого сценария; незавершённые изменения оборачивались `SAVEPOINT` / `ROLLBACK`.

| Проверка | Без защиты | После установки | Итог |
|---|---|---|---|
| INSERT новой банки в CLOSED | INSERT ACCEPTED | INSERT REJECTED: `Load order manifest is locked` | Защита вставки подтверждена |
| INSERT в DRAFT | — | INSERT ACCEPTED, транзакция отменена | Редактирование черновика сохранено |
| DELETE из CLOSED | DELETE ACCEPTED | DELETE REJECTED: `Load order manifest is locked` | Защита удаления подтверждена |
| Подмена `unit_id` в CLOSED | UPDATE без изменения значения был принят | Реальная замена отвергнута: `Load order manifest is locked` | Защита идентичности подтверждена |
| `PREPARED → RETURNED` при `IN_PROGRESS` | — | RETURN ACCEPTED, откат | Разрешённый переход не заблокирован |
| `PREPARED → LOADED` при `IN_PROGRESS` | — | LOAD ACCEPTED, откат | Разрешённый переход не заблокирован |
| `RETURNED → PREPARED` при `CLOSED` | — | REJECTED: `Invalid load order item status transition` | Недопустимый переход заблокирован |
| `CLOSED → DRAFT` с обнулением `closed_at` | REOPEN ACCEPTED | REOPEN REJECTED: `Load order details are locked` | Совокупная защита сработала |

В копии на момент завершения было установлено **8 триггеров**: четыре для `load_order_items` и четыре для `load_orders`. Последний тест **не изолирует** причину отказа до конкретного триггера: сообщение принадлежало охране реквизитов. Не заявлять, что все сочетания статусов испытаны.

**Обязательная доработка:** встроить триггеры в чистую схему (см. v1.1), запустить независимые тесты на новой БД, добавить сценарии неверного GTIN, двойной резервации экземпляра между заданиями, сбойной транзакции, устаревшего ACK и несанкционированных переходов. Триггеры не заменяют серверную валидацию.
