# МТА — товарный учёт: технический проект схемы v1.0

**Дата:** 21.10.2026  
**Статус:** DRAFT / на рассмотрение Саши и Ромы. Не применять к действующей `mta.db`.

## 1. Цель

Ввести единый каталог маркируемых товаров, постоянное хранение индивидуальных кодов GS1 Data Matrix и двухэтапный процесс **подготовка на складе → фактическая загрузка в МТА**. Приоритет — простота MVP, сохранение истории и безопасная повторная отправка запросов.

## 2. Границы и принятые решения

- Один канал одновременно содержит только один вид товара; проверка физической совместимости выполняется человеком.
- `product_id` генерируется автоматически как `PRD-000001`; GTIN — уникальный идентификатор товарной позиции в каталоге; название — одно поле; цена — в конфигурации аппарата.
- От одного сканирования GS1 Data Matrix получаем GTIN и индивидуальный код. Храним исходные данные сканирования **без потерь**, включая разделители. Прототип использует `BLOB`, обработку FNC1 / GS и синтаксиса GS1 реализует сервер.
- Исходный состав задания замораживается при переводе из `DRAFT` в `PREPARED`. Задание закрывается оператором только после разбирательства со всеми экземплярами.
- Повторное сканирование у аппарата подтверждает физическую загрузку; частичная загрузка и догрузка допускаются; незагруженные коды не исчезают.
- Сканирование в незавершённой сессии можно отменить с обязательным физическим извлечением ошибочно загруженной банки.
- Сканирование само по себе **не меняет остаток**. Завершение сессии применяет изменение остатка один раз, атомарно; учитываются только `SCANNED` (не `REMOVED`) позиции.
- В один момент у одного МТА может быть только одна сервисная сессия. При потере связи активная сессия сохраняется, продажи заблокированы. Сервисная механическая выдача не влияет на товарный учёт.
- Для окончания обслуживания обязательна подтверждённая синхронизация остатка и его версии с ESP32. Нельзя перезаписывать остаток поверх неподтверждённых событий NVS.
- Продажи уменьшают **количественный остаток**, но не присваивают конкретным кодам произвольный `SOLD`.
- При инвентаризации оператор сканирует все экземпляры и возвращает их в аппарат. При выгрузке сканирует извлечённые экземпляры. Списание товара — вне зоны ответственности МТА.

## 3. Файлы и назначение

`MTA_inventory_schema_v1_DRAFT.sql` — **самостоятельный тестовый прототип**, а НЕ SQL-миграция. Создаёт `devices` как минимальный стендовый справочник, а также: `products`, `product_units`, `device_channels`, `inventory`, `device_prices`, `load_orders`, `load_order_items`, `service_sessions`, `load_sessions`, `load_session_items`, `stock_operations`, `unit_movements`.

### Основные связи

```text
products 1 ── N product_units
products 1 ── N load_orders ── N load_order_items ── 1 product_units
 devices 1 ── N device_channels ── 1 inventory
 devices 1 ── N service_sessions ── 0..1 load_sessions ── N load_session_items
 load_sessions N ── 1 load_orders
 stock_operations / unit_movements: журнал подтверждённых изменений
```

`load_orders.planned_quantity` намеренно **не хранится**: первоначальный размер задания = количество строк в `load_order_items`; после `PREPARED` их состав неизменен.

`load_order_items.item_status` — результат обработки экземпляра **в рамках задания**, а не факт текущего физического наличия. `product_units.last_known_status` — последний подтверждённый этап, не доказательство наличия после продаж. Для точной истории используется `unit_movements`.

## 4. Принципиальные сценарии

### Подготовка
1. Авторизованный оператор сканирует маркируемые экземпляры, сервер валидирует код и GTIN, исключает дубли/конкурирующее резервирование.
2. Создаётся `load_orders(DRAFT)`, наполняется `load_order_items`.
3. После подтверждения `PREPARED` состав фиксируется. Остаток аппарата не меняется.

### Загрузка / догрузка
1. Оператор заходит в интерфейс аппарата по служебному QR-коду, открывает сервисную сессию `LOAD` и связанную `load_sessions(OPEN)`. Контроллер подтвердил запрет покупательских продаж.
2. Коды повторно сканируются; они должны принадлежать неизменному составу задания и соответствовать товару и каналу.
3. Ошибочно сканированную банку можно исключить до завершения. Повтор запроса не создаёт второй учётной позиции.
4. В транзакции: проверка сессии, фактически подтверждённых кодов, изменения item_status, вставка **одной** `stock_operations`, увеличение `inventory.quantity` и `inventory_version`, переход `load_sessions` в `COMPLETED`.
5. Остаток и версия доставляются ESP32 и сохраняются в NVS, контроллер подтверждает; только затем завершается общая сервисная сессия и разрешаются продажи.
6. Незагруженные банки остаются в исходном задании `PREPARED`; допускается новая загрузочная сессия того же задания.

### Закрытие задания
Задание переводится в `CLOSED` **явно** оператором, когда каждый экземпляр либо уже загружен по этому заданию, либо оформлен как возвращённый на склад. Исторический список не удаляется.

## 5. Что обеспечивает сама SQL-схема

- Уникальный GTIN и полный код маркировки.
- Существование товаров, аппаратов, каналов и экземпляров через внешние ключи.
- Неотрицательный остаток и монотонную версию (`inventory_version` должна увеличиваться прикладной транзакцией).
- Не более одной сервисной сессии со статусом `OPEN`/`RECOVERY_REQUIRED` на аппарат (частичный UNIQUE-индекс).
- Принадлежность каждой записи сканирования конкретному заданию и сессии через составные внешние ключи.
- Уникальность `source_session_id` в журнале `stock_operations` для защиты от повторной регистрации одной подтверждённой операции.

## 6. Что предстоит Роме реализовать в коде / тестах

Ограничения между таблицами не полностью выражены SQL: проверка, что `product_units.product_id` совпадает с `load_orders.product_id`; запрет одновременно резервировать экземпляр в разных активных заданиях; неизменность подготовленного задания; согласованность статусов; допустимость новой сессии; физически подтверждённая загрузка; разрешение смены товара в канале только после полной выгрузки; проверка GTIN и GS1-структуры; полноценные сценарии возврата, выгрузки и инвентаризации.

Для всех операций изменения остатков необходимы транзакции и проверки идемпотентности. Необходимо разработать сериализацию снимка остатков с подтверждением версии ESP32 и обработкой накопленных событий NVS. Успешная запись в SQLite **не означает**, что ESP32 уже получил новый остаток.

Также позже понадобится отдельный журнал обращений к ГИС МТ / «Честному знаку» со статусами отправки и подтверждения: внутренняя складская операция не равна автоматически выполненной государственной операции.

## 7. Совместимость и ограничения прототипа

- В архиве сервера `MTA-project-cleanup.zip` имеется `mta_schema.sql` со старыми `products(product_id, name)` и `inventory(device_id, product_id, quantity)`; новый проект **несовместим напрямую** с этими таблицами и с текущими SQL-запросами `mta_server.py`.
- Прототип не является миграцией и не содержит полноценной бизнес-логики. Каталог SQL не заменяет сервис проверки кодов. Для проверки используется только новая БД SQLite **в памяти**.
- На реальном ESP32 осталось неподтверждённое событие `MTA-001-E000000001`; смена схемы до урегулирования очереди и резервного копирования базы недопустима.
- Нужны отдельные решения: учёт старых записей (`WATER`, `COLA`), конфигурация канала, операторская авторизация, применение цен, способы блокировки продаж и возобновления обслуживания.
- Для хранения и обработки полных кодов маркировки необходима политика ограниченного доступа: не записывать коды в логи, маскировать в UI и не включать в публичные тестовые данные.

## 8. Рекомендуемые проверки следующей итерации

1. Две одинаковые GTIN и два одинаковых индивидуальных кода отклоняются.
2. Сканирование одного экземпляра в разных заданиях не приводит к двойному резервированию.
3. Загрузка 18 из 30, закрытие сессии, догрузка 9, возврат 3, ручное закрытие задания.
4. Отмена сканирования до завершения не влияет на остаток.
5. Повтор `COMPLETED` не изменяет количество второй раз.
6. Обрыв связи до/после коммита SQLite с восстановлением.
7. Два одновременно начатых обслуживания одного аппарата: второе отклоняется.
8. Смена ассортимента возможна только после полной выгрузки старого.
9. При инвентаризации не меняется состав товаров, пока оператор не подтвердил возвращение всех экземпляров.
10. Подтверждение ESP32 старой версии остатков не разрешает завершить обслуживание.
