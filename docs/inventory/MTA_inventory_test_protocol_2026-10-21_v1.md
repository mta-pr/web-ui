# МТА — протокол первичного испытания товарного учёта

**Дата:** 21.10.2026  
**Редакция:** 1.0 — протокол наблюдаемых результатов; для ревью Ромой  
**Статус:** контрольный позитивный сценарий выполнен; серверный API, реальное сканирование и ESP32 не испытаны

## 1. Цель и границы испытания

Проверить, что проектная SQLite-схема и отдельные Python-тесты способны провести одну партию из 30 условных индивидуально маркированных экземпляров через складскую подготовку, две загрузки, возврат и закрытие задания, сохраняя количественный остаток и журнал операций.

**Испытательная среда:** Windows, `C:\MTA-Test\Inventory-Test`, отдельная `MTA_inventory_TEST.db` (SQLite через `uv run --no-project python`). SQL-источник — `MTA_inventory_schema_v1_DRAFT.sql`. Условный товар `PRD-000001`, GTIN `00000000000000`, 30 синтетических кодов `MTA-TEST-UNIT-0001` … `0030` в `BLOB`, аппарат `MTA-001`, канал 1. Это **не действительные коды «Честного знака»**. В рабочую серверную `mta.db` никаких изменений не вносилось; реальный ESP32 не подключался.

Подтверждение результатов основано на выводах CMD, присланных оператором в ходе шагов 1–35, и содержимом тестовых SQL/Python-файлов; это **не независимый аудит фактической базы пользователя**.

## 3. Что испытание НЕ доказывает

1. Не реализованы и не протестированы реальные HTTP-обработчики FastAPI, учёт через смартфон, авторизация оператора, приём/валидация реальных GS1 Data Matrix и интеграция с «Честным знаком».
2. Не проверены взаимодействие с физическим ESP32, запись в реальную NVS, сетевые сбои, задержанные/устаревшие ACK, гонки синхронизации и восстановление незавершённого сервиса.
3. Идемпотентность продемонстрирована **в двух конкретных тестовых скриптах**, а не гарантирована для будущего API.
4. Наличие `PREPARED`/`CLOSED` в таблице задания **само по себе не запрещает** непосредственное изменение состава `load_order_items`; правило неизменяемого манифеста нужно реализовать и протестировать.
5. Уникальность `(load_session_id, unit_id)` не гарантирует запрет повторного учёта **того же экземпляра в другой сессии или активном задании**.
6. Не испытаны нехватка товара, конкурирующие транзакции, неверный `product_id`, несовпадение канала/устройства, чужой код, отключение питания/сети в середине операции и откат при ошибке после части SQL-действий.
7. В проектном SQL нет готового надёжного юридически значимого отчёта о выводе кодов маркировки из оборота. Индивидуальный продаваемый экземпляр невозможно достоверно определить только по количественной продаже МТА.
8. Тестовая SQL-схема — **не миграция** для действующей серверной базы; её нельзя применять напрямую поверх `mta.db`.

## 4. Выявленные технические замечания

- При первом подсчёте таблиц ошибочно ожидались 14; фактически в SQL-файле **13** пользовательских таблиц. На корректность самой структуры это не повлияло.
- Попытка установить `scan_status='REMOVED'` без заполнения `removed_at` закономерно завершилась `CHECK constraint failed`; исправленная команда прошла. Это подтверждает конкретную проверку целостности.
- Тестовый сценарий требует отдельно оговорить смысл состояния `PARTIALLY_LOADED` и правило перехода к `CLOSED` после подтверждённого возврата оставшихся экземпляров.
- `product_units.last_known_status` — лишь последний подтверждённый статус; после продаж без индивидуального считывания он не определяет фактическое нахождение конкретной банки.
- JSON-файл `MTA_mock_ESP32_NVS.json` — только имитация NVS; не является доказательством сохранения данных самим ESP32.

## 5. План негативных испытаний (проводить по одному)

| Приоритет | Испытание | Ожидаемая политика |
|---|---|---|
| P0 | Попытка изменить состав задания после `PREPARED` или `CLOSED` | Отклонение через будущую серверную бизнес-логику/защиту БД; история неизменна |
| P0 | Та же `unit_id` в другой активной загрузке/задании | Запрет двойного резервирования/учёта с учётом исторических заданий |
| P0 | Повторное подтверждение операции через новый запрос и конкурентные запросы | Один учёт, один набор движений, одна версия увеличения |
| P0 | Обрыв между обновлением SQL и подтверждением имитатора | Сервис не закрывается до восстановления и согласованного ACK |
| P0 | Просроченный ACK версии 1 при серверной версии 2 | Запрет завершения обслуживания |
| P1 | Неверный товар/GTIN, чужой экземпляр, другой канал | Отказ без изменения данных |
| P1 | Попытка открыть вторую активную сервисную сессию | Отказ уникального индекса |
| P1 | Попытка возврата уже загруженной банки как «не загруженной» | Отказ без изменения остатка |
| P1 | Искусственная ошибка внутри многошаговой транзакции | Полный откат всех её изменений |
| P1 | Повторное закрытие задания и исправление после закрытия | Никаких несанкционированных изменений |

## 6. Рекомендованный порядок работы

1. Сохранить этот протокол в `docs/inventory` репозитория как документ ревью (без изменения рабочей БД).
2. Выполнить негативные тесты на **отдельной копии** `MTA_inventory_TEST.db` или с явным `ROLLBACK`, не нарушая зафиксированный успешно завершённый сценарий.
3. Исправить выявленные пробелы схемы и определить контракт API/операций; изменения согласовать с Ромой.
4. Подготовить тестируемые миграции и план совместимости с действующим сервером; отдельно провести интеграционные испытания с реальным ESP32.

## 7. Приложения и воспроизводимость

- `MTA_inventory_schema_v1_DRAFT.sql` — тестовая проектная схема.
- `MTA_inventory_architecture_v1_REVIEW.md` — исходные архитектурные правила.
- `MTA_test_finalize_load_25.py`, `MTA_test_finalize_load_3.py` — два теста подтверждения загрузок.
- `MTA_test_mock_esp_ack.py`, `MTA_test_mock_esp_ack_2.py` — два теста синхронизации с JSON-имитатором.
- `MTA_inventory_TEST.db` — тестовая БД хранится **на компьютере оператора**, к этому протоколу не прилагается.

**Вывод:** основной позитивный сценарий продемонстрировал согласованный количественный учёт 30 тестовых единиц и отсутствие повторного начисления в проверенных скриптах. Для вывода о готовности к внедрению обязательны негативные, интеграционные и отказоустойчивые испытания.
