# Передача проекта товарного учёта МТА — Роме

**Дата:** 22.10.2026 · **Статус:** handoff / архитектура на ревью, не production-ready.

## Назначение

Саша и ChatGPT исследовали модель товарного учёта маркируемой продукции для МТА: каталог, неизменный список подготовленных экземпляров, частичная загрузка, догрузка, возврат на склад, операции с количественным остатком, повторные запросы и имитация ACK от ESP32. **Рома принимает владение сервером и базой**, Саша продолжает работу над прошивкой и платёжным терминалом. Эти материалы предлагаются как точка старта, а не как обязательное техническое решение.

## С чего начать

1. `MTA_inventory_architecture_v1_REVIEW.md` — исходные договорённости, бизнес-сценарии и границы ответственности.
2. `MTA_inventory_schema_v1_1_REVIEW.sql` — **единая самостоятельная схема v1.1**, включающая исходные 13 таблиц и 8 испытанных защитных триггеров.
3. `MTA_inventory_test_protocol_2026-10-21_v1.md` — результаты позитивного контрольного сценария **до интеграции триггеров**; протокол не покрывает последующие шаги 36–55.
4. `NEGATIVE_TESTS_2026-10-21.md` — наблюдавшиеся негативные тесты/исправления.
5. `test_inventory_schema_v1_1.py` — новый автономный smoke-test на чистой SQLite в памяти: не изменяет рабочие базы.
6. Прочие `MTA_test_*.py`, `MTA_install_*.py` — исторические вспомогательные скрипты; требуют локальных тестовых БД и конкретных данных, **не запускать против сервера**.

## Как проверить без опасности

Установлен Python 3.11+ (SQLite 3.31+). Из папки с файлами выполнить:

```cmd
uv run --no-project python test_inventory_schema_v1_1.py
```

Скрипт использует `:memory:`, не создаёт файлов БД. **Не выполнять** `MTA_inventory_schema_v1_1_REVIEW.sql` поверх существующей `mta.db`.

## Что НЕ реализовано и требует решения Ромы

- Никаких миграций старых `products`/`inventory` и исторических SALE; несовместимые текущие таблицы сервера. Сначала резервная копия и стратегия миграции.
- API: приём сканов, GS1 Data Matrix (включая ASCII GS/FNC1), валидация GTIN/кода, операторская авторизация и журнал действий, работа смартфона.
- Проверки между разными заданиями/сессиями: совпадение продукта и устройства, недопущение двойного резервирования/списания экземпляра.
- Гарантированная идемпотентность API и многопоточные/конкурентные проверки. Тестовые Python-скрипты подтверждали только конкретные сценарии.
- ACK/NVS настоящий ESP32 **не проверялся**; JSON-имитатор — не контроллер. Не позволять возобновлять продажи без согласования версии, очереди событий и получения подтверждения.
- Закрытие заказа в чистой схеме ограничено SQL-проверками состава/активного сервиса, но полноту внешнего подтверждения физической загрузки и синхронизации проверяет сервер. `last_known_status` не сообщает, какая банка продана при количественном SALE.
- Проверить отдельными тестами правила переходов `load_orders`, запрет подмены GTIN, связи между экземплярами и заданиями, работу при сбоях, приоритет механической безопасности.
- Вывод кодов из оборота в «Честном знаке» и регуляторная интеграция **отдельный проект**, прототип её не заменяет.

## Что можно коммитить

Только **документацию, SQL-прототип и тестовые `.py`** в `docs/inventory/` (или другое согласованное с Ромой место). Не добавлять *.db, JSON-имитатор NVS, пароли, mta_secrets.h, реальные коды маркировки или скриншоты с чувствительными данными. Коммит лучше отдельный, в существующей совместно согласованной ветке; не сливать в `main` без ревью.

## Взаимодействие с прошивкой

Нужен отдельный контракт ESP↔сервер: запрет продаж на время обслуживания, атомарное применение снимка `(device_id, channel_id, product_id, quantity, inventory_version)`, ACK после NVS, защита от устаревшей версии и урегулирование неотправленных событий SALE. У действующего ESP было накопленное неподтверждённое событие `MTA-001-E000000001` (HTTP 400); не очищать NVS без решения причины.
